# AGENTS.md — точка входа для агентов

Общий регламент работы над пакетом **bubble** для Claude Code и Codex.
`CLAUDE.md` ссылается сюда, других точек входа нет. Правила отсюда старше
привычек инструмента; всё, чего здесь нет, решается по репозиторию,
а не по памяти инструмента.

Уклад тот же, что в соседних пакетах владельца (navigation_node,
ansi_escape_codes, scopo): здесь он пересказан под один небольшой виджет и один
пример.

## 1. Начало сессии — восстановление контекста

Сессия может оборваться в любой момент. Порядок восстановления:

1. **`docs/handoff.md`** — состояние **сейчас**: что зелено, что открыто, что
   ждёт решения владельца, какой следующий безопасный шаг. Сюда же идут находки
   и предложения агента.
2. **`docs/backlog.md`** — список владельца: чего он хочет.
3. По необходимости — **`docs/architecture.md`** (как пузырь устроен внутри
   и что в нём легко сломать) и **`docs/records/`** (история правок).
4. Сверка с репозиторием: `git log --oneline -10`, `git status`.

Пока не прочитан `docs/handoff.md`, никаких правок в коде.

**Код, тесты и git старше любого документа.** Расходится документ
с репозиторием — прав репозиторий. Обратное тоже верно: не переписывать
документ под своё впечатление, не проверив по коду.

## 2. По ходу и в конце сессии — поддержание состояния

**`docs/handoff.md` должен быть актуален всегда**, а не только в конце: сессия
обрывается без предупреждения, и всё, что не записано, теряется. Обновлять его,
когда сделан заметный шаг (коммит, пройденная проверка, найденный дефект),
когда меняется направление работы, перед длинной операцией и в конце сессии —
обязательно.

Чего в нём быть не должно: пересказа истории коммитов (её знает git), разбора
законченных эпизодов (это `docs/records/`) и пожеланий владельца (это
`docs/backlog.md`). Handoff отвечает на «где мы стоим», а не на «как мы сюда
пришли». Волна закончилась — её handoff уезжает в `docs/records/` записью жанра
`report`, а `docs/handoff.md` переписывается под новое состояние.

## 3. Бэклог владельца

`docs/backlog.md` — что владелец хочет сделать с пакетом. **Агенты в него
не пишут**: читать — да, брать пункт в работу — да, заводить свои пункты — нет.
Нашли что-то по ходу — в `docs/handoff.md`, а владелец сам решит, переносить ли
это в бэклог.

Бэклог не пуст, а обязательной работы нет — предложить владельцу взять пункт.
Взятый и доведённый до конца пункт **удаляется из бэклога** в том же коммите,
что и работа; выполненный частично — сокращается до оставшегося. Формулировки
владельца без нужды не переписывать.

## 4. Что это за пакет

Flutter-виджет `Bubble` — пузырь сообщения чата с необязательным хвостиком.
Одна библиотека `lib/bubble.dart` из пяти `part`-файлов; публичны все её
классы: `Bubble`, `BubbleNip`, `BubbleStyle`, `BubbleEdges`, `BubbleClipper`,
`BubblePainter`. Отдельно, второй библиотекой, —
`package:bubble/issue_clipper.dart` (`IssueClipper`): отладочные контуры для
примера, публичны по недосмотру, но публичны (см. `docs/handoff.md`).

Пакетом пользуются: на 2026-10-15 — 269 звёзд на GitHub, 604 лайка и ~17.5 тыс.
скачиваний за 30 дней на pub.dev. Поэтому **любая правка публичного API или
видимого поведения — геометрии, умолчаний, порядка отрисовки — идёт через
решение владельца**, а не «заодно».

Последняя изданная версия — **1.2.1 от 2021-03-10** (тег `1.2.1`). Всё, что
сделано после, лежит в разделе `## Unreleased` в `CHANGELOG.md`; версию
в `pubspec.yaml` не бампать без слова владельца.

## 5. Проверки

Тулчейн — **Flutter 3.27.0 через fvm** (`.fvmrc`, `.fvm/`
и `.vscode/settings.json` не под контролем версий). Это ровно тот пол, что
заявлен в `pubspec.yaml`, так что локальный прогон и есть проверка пола. CI
(`.github/workflows/ci.yml`) гоняет то же на 3.27.0 и на свежем stable.

```sh
fvm dart pub publish --dry-run       # 0 warnings; на чистом дереве
sh docs/ru/check.sh                  # переводы отвечают оригиналам
fvm dart format --set-exit-if-changed lib test example/lib example/test
fvm flutter analyze                  # корень; обходит и example/
fvm dart doc --dry-run               # 0 warnings, 0 errors
fvm flutter test                     # все зелёные; число — в docs/handoff.md
(cd example && fvm flutter analyze && fvm flutter test)
```

Перед коммитом в `master` проходят все. Утверждать «работает» без вывода
команды нельзя: сначала прогон, потом заявление.

**Картинки в `test/bubble_clipper_test.dart` — снимок формы пузыря.** Каждая —
контур 32×20, растрированный по центрам пикселей; сняты с 1.2.1 до первой
правки кода. Тест упал после правки, которая форму менять не должна, — значит,
она её поменяла. Если форма меняется намеренно (решение владельца), картинка
обновляется в том же коммите, а `CHANGELOG.md` называет изменение.

**Прогнал что-то другим SDK** — глобальным `flutter` с `PATH` или через
`fvm spawn <версия>` — сразу после этого
`fvm flutter clean && fvm flutter pub get`: чужой движок оставляет
в `.dart_tool` свой кеш, и следующий прогон падает без дефекта в коде.

**Что не публикуется** — перечислено в `.pubignore`: `docs/`, `AGENTS.md`,
`CLAUDE.md`, `.github/`, русские зеркала, платформенные папки примера и все
скриншоты, кроме `screenshots/example.png` (его называет `pubspec.yaml` для
витрины pub.dev; остальные README берёт с GitHub по абсолютным ссылкам).

## 6. Как здесь принято работать

- **Сначала тест.** Дефект — сперва падающий тест, потом исправление.
  Исправил — откати правку и убедись, что тест падает.
- **Ожидаемые значения снимаются пробником с живого кода**, а не выводятся
  рассуждением. Тест падает — объяснить почему, а не подгонять ожидание.
- **Не расширяй объём молча.** Нашёл смежную проблему — запиши
  в `docs/handoff.md`, а не чини заодно.
- **Отчитывайся честно.** Тесты упали — покажи вывод.
- Правки в `lib/` без обновления `CHANGELOG.md` не заканчиваются.

## 7. История правок — `docs/records/`

Спеки, планы, отчёты, ревью — сюда, а не в стандартные пути скиллов
(`superpowers:writing-plans` по умолчанию пишет в `docs/superpowers/plans/` —
итог всё равно кладётся в `docs/records/`, второй копии не оставлять).

- Имя файла **`YYYY-MM-DD[N]-name-kind.md`**, квадратные скобки — литеральные;
  `[N]` — порядковый номер записи за день, начиная с `[1]`; дата — дня
  написания.
- **`kind` в конце имени обязателен** — одно слово о том, что это за бумага:
  `design` (устройство и API), `plan` (план работ), `report` (отчёт о волне
  правок, о разборе дефекта, о предмержевом ревью одной работы), `review`
  (полное ревью всего проекта). Нужного слова нет — взять своё по тому же
  принципу.
- Каждый файл начинается с H1 и **шапки текущего состояния** под ним:

  ```markdown
  > **Состояние на YYYY-MM-DD:** что с этой работой сейчас — сделано и
  > закоммичено (коммит), брошено, частично сделано, пересмотрено позже.
  > **Что это:** одна фраза о содержимом.
  > **Связанные записи:** имена других файлов в `docs/records/`.
  ```

- Шапку обновляют, когда судьба работы изменилась; сам текст записи
  не переписывают — он исторический.
- **Вердикт по находке ревью — абзацем в конце этой находки, в самом файле
  ревью**, с жирным зачином:
  `**Вердикт: исправлено** — коммит `abc1234`. Далее почему.` Отдельного
  подзаголовка не заводить; вставлять строки, а не пересобирать абзацы, и после
  правки проверить `git diff`: удалённых строк быть не должно.
- Записи в `docs/records/` не поддерживаются как справка: расходятся с кодом —
  верен код.

## 8. Git и GitHub

- Ветка по умолчанию — **`master`** (у соседей `main`; переименование — решение
  владельца, оно трогает чужие форки и ссылки).
- **Не коммить чужие правки вместе со своими.** Перед коммитом — `git status`
  и `git diff`; добавлять в индекс поимённо то, что сделано этим заходом,
  а не `git add -A`. Постороннее в дереве не трогать — ни коммитить,
  ни удалять, — сказать о нём владельцу.
- Сообщения коммитов — по-английски, с префиксом `feat:`, `fix:`, `docs:`,
  `refactor:`, `test:`, `chore:`; один фикс — один коммит; тело объясняет
  «почему», а не «что».
- **Push, ответы в issues и PR, закрытие issues, мерж чужих PR — только
  по слову владельца.** Это публичные действия от его имени. На 2026-10-15
  разрешения на push нет.
- Force-push и переписывание истории `master` — никогда без прямой просьбы.

## 9. Публикация

**Публикация на pub.dev — это связка целиком, одним заходом и подряд:**

1. коммит `Release X.Y.Z` (в нём же бамп версии в `pubspec.yaml` и заголовок
   раздела `CHANGELOG.md` с датой вместо `Unreleased`);
2. тег `X.Y.Z` (два последних тега — `1.2.0` и `1.2.1`, без `v`);
3. `git push` коммита и тега;
4. `dart pub publish`.

**Ни одну часть по отдельности.** Тег без загрузки, коммит `Release` «чтобы
стоял», загрузка с непушенного дерева — это половина релиза, которую уже
не собрать обратно: версию с pub.dev не удалить.

**Подготовку к публикации делать свободно** — это обычные правки в дереве:
раздел CHANGELOG, README и его перевод, прогон проверок,
`dart pub publish --dry-run`. Разрешения они не требуют и разрешением
не становятся. Бамп версии подготовкой не считается: он первый шаг связки.

**Разрешение на публикацию — только явное и только на эту связку.** Оно
не переносится на следующий релиз и не выводится из готовности релиза. «Всё
готово к публикации», пройденный чеклист, зелёный CI — не разрешение.
Разрешение — отдельный запрос владельца, состоящий только из просьбы
опубликовать. Если в сообщении есть хоть что-то ещё — правка, вопрос,
«а заодно», — не запускать из связки ничего, даже если слово «публикуй» стоит
в нём прямым текстом.

**Не спрашивать — отказать.** Не задавать вопроса «публиковать?», не выносить
решение на подтверждение: сделать остальную работу и отказать в публикации,
назвав условие. Сомневаешься — не публикуй. Отказ стоит одного сообщения,
ошибка стоит номера версии.

## 10. Язык

- Документы для владельца и агентов (`AGENTS.md`, `docs/`, всё
  в `docs/records/`) и общение с владельцем — **по-русски**.
- Публичные артефакты — **по-английски**: `README.md`, `CHANGELOG.md`,
  `example/README.md`, весь код и комментарии в `lib/`, `test/`, `example/`
  (включая dartdoc), сообщения коммитов, тексты ошибок.

**Русские зеркала публичных документов** лежат рядом с оригиналами:
`README.ru.md`, `example/README.ru.md`. Правка оригинала не заканчивается без
правки перевода **в том же коммите**; после правки — `sh docs/ru/stamp.sh`
(переносит blob-хеш оригинала в шапку перевода), расхождение ловит
`sh docs/ru/check.sh`. Структура, порядок разделов и код примеров в зеркале
те же — переводятся проза и комментарии внутри примеров.

`stamp.sh` не читает текст и не отличит обновлённый перевод от устаревшего.
Запуск «чтобы проверка замолчала» — это ложь в проверке, а не её прохождение.

## 11. Чего не делать без слова владельца

- Публикацию и всё, что в неё входит (раздел 9), и бамп версии.
- Push, действия на GitHub от имени владельца (раздел 8).
- Менять публичный API или видимое поведение — в том числе чинить дефекты,
  которые его меняют: дефекты записаны в `docs/handoff.md`, решение по ним
  за владельцем.
- Поднимать пол SDK (`^3.6.0`, Flutter 3.27.0) — отдельный заход: с языком 3.7
  `dart format` переходит на высокий стиль и правило `require_trailing_commas`
  в `analysis_options.yaml` придётся снять.
- Заводить пункты в `docs/backlog.md`.
